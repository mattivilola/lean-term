# Released-app benchmark — 5 November 2026

**Lean Term 0.1.2 kept the prototype's median typing-response range.**
Two shell medians were **24.79 / 24.92 ms**; Vim insert-mode typing was
**25.14 ms**. The first small product check is encouraging: the polished native
interface did not show an obvious median-response regression in these runs.
This is a local comparison, not a universal fastest-terminal claim.

## Conditions and reproducibility

The installed, signed/notarized `/Applications/Lean Term.app`, version 0.1.2,
source `756dee2375af089f000b7239fc7d310465427210`, was tested without rebuilding
or changing its executable. Its SHA-256 and sanitized conditions are in
[conditions.json](2026-11-05-actual/conditions.json). All raw readings, including
setup launch attempts, are in [the data directory](2026-11-05-actual/).

Same M3 Max MacBook Pro / 36 GB as the [initial experiment](2026-11-04.md):
macOS 27.0.1, Xcode 27.1 / Swift 6.4, AC power, built-in Retina display reporting
120 Hz maximum and scale 2. Both experiments used Menlo Regular 13, 120 × 40
cells, an opaque dark background and 10,000 scrollback lines. This app used its
Graphite palette; the original fixture used its flat dark palette. Actual variable
refresh and background workstation load were not fixed. No contemporaneous
reference-app rerun was performed.

## Typing and TUI response — primary result

Typometer 1.0.1 / Java 21, synchronous AWT Robot capture, 200 samples per run,
150 ms delay, intermediate pauses off. Run order: shell A → Vim → shell B.
Shell runs used `/bin/zsh -f` with a short prompt. Vim 9.1.1752 used an unnamed
insert-mode buffer with no user config, plugins, swap or viminfo file. The welcome
screen was cleared before measurement. All **600 samples** are retained.

| Target / run | Median ms | p95 ms |
|---|---:|---:|
| **Lean Term 0.1.2 — shell A** | **24.79** | **55.25** |
| **Lean Term 0.1.2 — Vim** | **25.14** | **41.72** |
| **Lean Term 0.1.2 — shell B** | **24.92** | **38.01** |
| Earlier CG fixture | 22.11 | 34.92 |
| Earlier CG confirmation | 27.05 | 49.03 |
| Earlier Metal fixture | 34.09 | 69.63 |
| Earlier Metal confirmation | 32.10 | 55.18 |
| Earlier Ghostty 1.3.1 reference | 31.00 | 58.08 |

The released app's shell medians lie between the earlier CG medians. Its tail
varies, particularly in shell A; report both runs rather than choosing the best.
The historical Metal and Ghostty figures provide context, not a fresh controlled
ranking. There is no earlier Vim result: this establishes the first simple TUI
baseline, covering insert-mode typing rather than every TUI workload.

These are **synthetic OS-input-to-screen-capture timings**, including capture
overhead, not physical key-to-photon latency. Typometer required the same manual
start/focus action as before; no permission-interrupted run is included.

## Memory — secondary result

| GUI physical footprint | Lean Term 0.1.2 | Earlier CG fixture |
|---|---:|---:|
| Idle | **58.5 MiB** | 49.9 MiB |
| Filled scrollback | **81.2 MiB** | 64.5 MiB |

Today's figures are medians of 10-second samples from one task-owned GUI process,
with one 120 × 40 window. Shell/TUI/Python and updater helper processes are excluded.
The idle sample followed the typing/Vim tests. Output began only after that sample
finished. The existing workload then wrote the same three approximately 10 MiB
ASCII and three mixed ANSI/Unicode payloads as the initial experiment; hashes and
120 × 40 dimensions match. The final completion marker was visually observed,
then a separate quiet filled-scrollback sample was taken. Each footprint stayed
constant throughout its 10-second sample. This is not a leak/long-soak test.

The observed increases are about **8.6 MiB idle / 16.7 MiB filled**. The app has
more UI/updater integration and different warm-up history; this comparison does
not isolate the cause of that increase. The earlier filled value was a snapshot,
not an equivalent repeated memory study. Metal's invalid idle interval remains
excluded. CPU sampling used the corrected Mach timebase; idle GUI CPU was about
0.0011% of one core during this short observation.

The workload also recorded writer-completion medians of 146.7 MiB/s ASCII and
56.0 MiB/s mixed output (earlier CG: 192.0 / 57.7). These are PTY intake rates,
not rendered throughput, and are not the primary typing/TUI result.

## Launch — secondary result

Three sequential warm launches of the installed app reached the first on-screen
main window in **0.605 / 0.533 / 0.516 seconds**: **0.533 seconds median**.
Each started a fresh GUI process with temporary Menlo 13 / 120 × 40 placement
arguments and the normal account login shell. Each was closed through the app's
normal confirmation before the next launch.

The external [observer](../window_launch.swift) starts its clock immediately before
requesting the launch through NSWorkspace and polls WindowServer every 5 ms for
that PID's first on-screen main window. Window animation can still be in progress;
this endpoint is **neither first painted frame nor usable shell prompt**. Shell
startup files and launch-service overhead are part of the environment. This is
not a cold-cache measurement, and the initial experiment has no valid launch
baseline. Do not market it as sub-second cold startup or ready-to-type time.

Two exploratory launches are preserved separately: 2.995 s at the unmatched
110 × 34 setup size, and 0.486 s while validating matched placement. Neither is
part of the defined three-trial warm-launch median. The unmatched setup idle
sample is also retained separately and excluded from the matched memory table.

## Practical conclusion

The first released-app check supports continuing with the selected Swift/AppKit
and CoreGraphics stack: about 25 ms median response in this local capture test,
roughly 59 MiB idle GUI footprint, and about half a second to a window on warm
launches. The app carries more memory than the stripped fixture. Keep these
conditions attached to public claims; Rust remains untested, and no result here
establishes the fastest possible stack.
